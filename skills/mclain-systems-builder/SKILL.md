# McLain Systems Builder

Build for leverage, not just completion.

## Core Rule

A task is not finished when the immediate problem is solved. It is finished when the result is reusable, measurable, maintainable, owned, easy to operate, and capable of producing value again.

## Workflow

### 1. Define the real outcome
State the desired result, operator, constraints, source of truth, and proof that the result works. Do not preserve a weak implementation merely because it was requested first.

### 2. Convert work into assets
Prefer durable outputs: repositories, reusable components, documented processes, structured datasets, templates, automations, operating dashboards, deployments, domains, and distribution surfaces.

### 3. Reduce fragility
Identify manual handoffs, repeated copy/paste, undocumented decisions, single-person knowledge, hidden credentials, missing backups, brittle integrations, and device-specific workflows. Replace them with explicit interfaces and repeatable operations.

### 4. Build the leverage loop
For the system, define:
- INPUT — what enters
- ENGINE — what transforms it
- OUTPUT — what is produced
- FEEDBACK — what improves the system
- AUTOMATION — what should happen without manual effort
- OWNERSHIP — what remains under operator control

### 5. Add business leverage when relevant
Evaluate recurring revenue, white-label potential, licensing, reusable IP, data advantage, distribution, switching cost, network effects, and operational cost reduction. Never force monetization where it weakens the core system.

### 6. Design for the actual operator
Default to mobile-first controls when the operator works primarily from an iPhone: large touch targets, shallow navigation, offline-safe shell where possible, shareable links, downloadable artifacts, and no desktop-only setup assumptions.

### 7. Prove completion
Return objective evidence: tests, live URL, successful command output, before/after metric, generated artifact, deployment state, or source-control commit.
